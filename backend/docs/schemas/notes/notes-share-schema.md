# NoteGenius — Note Shares Database Schema

**Document:** `notes-share-schema.md`  
**Version:** 1.0  
**Status:** Confirmed  
**Database:** PostgreSQL  
**ORM:** Drizzle ORM

---

## 1. Purpose

The `note_shares` table manages explicit, recipient-specific access to notes in NoteGenius.

It allows note owners to share their notes with registered users identified by their `@user_handle`. Recipients receive **view-only access** and cannot modify the original note.

The schema preserves revoked share records for historical reference while enforcing a single active share per note-recipient pair.

## 2. Design Decisions

- Use a surrogate primary key, `internal_id`.
- Provide a public UUID, `public_id`, for external references.
- Reference notes through `notes.internal_id`.
- Reference recipients through `users.internal_id`.
- Permit only the note owner to create shares.
- Prohibit self-sharing through backend validation.
- Allow explicit sharing of both private and public notes.
- Preserve revoked share records using `revoked_at`.
- Create a new row when a revoked share is recreated.
- Block access when the note, recipient account, or owner account is ineligible.
- Use database-generated timestamps.
- Enforce timestamp ordering with a database `CHECK` constraint.
- Use `ON DELETE CASCADE` for note deletion and `ON DELETE RESTRICT` for recipient deletion.
- Avoid unnecessary columns such as `updated_at`, `revoked_by_user_id`, and `previous_share_id`.

## 3. Table Definition

```sql
CREATE TABLE note_shares (
    internal_id BIGSERIAL PRIMARY KEY,

    public_id UUID NOT NULL
        UNIQUE DEFAULT gen_random_uuid(),

    note_id BIGINT NOT NULL
        REFERENCES notes (internal_id)
        ON DELETE CASCADE,

    recipient_user_id BIGINT NOT NULL
        REFERENCES users (internal_id)
        ON DELETE RESTRICT,

    created_at TIMESTAMPTZ NOT NULL
        DEFAULT NOW(),

    revoked_at TIMESTAMPTZ NULL,

    CONSTRAINT note_shares_revoked_at_check
        CHECK (
            revoked_at IS NULL
            OR revoked_at >= created_at
        )
);
```

### 3.1 Column Specifications

| Column              | Type          | Constraints                            | Purpose                                          |
| ------------------- | ------------- | -------------------------------------- | ------------------------------------------------ |
| `internal_id`       | `BIGSERIAL`   | Primary key                            | Internal identifier for a share record           |
| `public_id`         | `UUID`        | Not null, unique, generated by default | Stable public identifier for external references |
| `note_id`           | `BIGINT`      | Not null, FK, cascade on delete        | Identifies the shared note                       |
| `recipient_user_id` | `BIGINT`      | Not null, FK, restrict on delete       | Identifies the recipient                         |
| `created_at`        | `TIMESTAMPTZ` | Not null, defaults to `NOW()`          | Records when the share was created               |
| `revoked_at`        | `TIMESTAMPTZ` | Nullable, validated by `CHECK`         | Records when the share was revoked               |

### 3.2 Revocation Semantics

- `revoked_at IS NULL`: the share is active.
- `revoked_at IS NOT NULL`: the share has been revoked.
- Revocation updates the existing row rather than deleting it.
- Re-sharing after revocation inserts a new row with a new `internal_id` and `public_id`.

The database constraint prevents a revocation timestamp from preceding the share's creation timestamp.

## 4. Indexes

### 4.1 Active Share Uniqueness

```sql
CREATE UNIQUE INDEX note_shares_active_unique_idx
ON note_shares (note_id, recipient_user_id)
WHERE revoked_at IS NULL;
```

**Purpose:**

- Prevent duplicate active shares for the same note-recipient pair.
- Support lookups of active shares by note and recipient.
- Allow a new share record after the previous share has been revoked.

The index is partial, so revoked historical records do not prevent re-sharing.

### 4.2 Recipient's Active Shares

```sql
CREATE INDEX note_shares_recipient_active_idx
ON note_shares (recipient_user_id, created_at DESC)
WHERE revoked_at IS NULL;
```

**Purpose:**

- Support the recipient's **Shared with me** inbox.
- Filter for active shares.
- Retrieve the newest shares first.

### 4.3 Note Share History

```sql
CREATE INDEX note_shares_note_history_idx
ON note_shares (note_id, created_at DESC);
```

**Purpose:**

- Retrieve all shares associated with a note.
- Include both active and revoked records.
- Sort sharing events from newest to oldest.

This full index complements the partial unique index. It supports historical queries that must include revoked records.

## 5. Relationships and Deletion Policies

### 5.1 Relationship to `notes`

```sql
note_id BIGINT NOT NULL
    REFERENCES notes (internal_id)
    ON DELETE CASCADE
```

- A note can have multiple share records.
- Permanent note deletion automatically deletes its associated share records.
- Soft deletion does not trigger the foreign-key cascade.
- The backend must deny access while the note is soft-deleted.

### 5.2 Relationship to `users`

```sql
recipient_user_id BIGINT NOT NULL
    REFERENCES users (internal_id)
    ON DELETE RESTRICT
```

- A user can receive multiple shares.
- Permanent recipient deletion is blocked while dependent share records remain.
- The account-deletion workflow must explicitly remove dependent share records before deleting the user.
- Recipient deletion and dependent-record cleanup should be handled transactionally where practical.

The note owner's relationship is resolved through `notes.user_id`. A separate owner column in `note_shares` is unnecessary.

## 6. Backend Authorization Rules

Database constraints alone do not enforce all sharing policies. The backend must implement the following checks.

### 6.1 Share Creation

Before creating a share, the backend must:

1. Authenticate the requester.
2. Verify that the requested note exists and is not soft-deleted.
3. Verify that the requester owns the note by comparing the authenticated user's internal ID with `notes.user_id`.
4. Resolve the recipient's `@user_handle` to `users.internal_id`.
5. Verify that the recipient account has `account_status = 'active'` and `deleted_at IS NULL`.
6. Reject self-sharing when the recipient ID equals the note owner's ID.
7. Insert the share with a database-generated `created_at`.
8. Handle concurrent duplicate-share attempts through the unique partial index and return an appropriate application-level response.

Only the note owner may create shares. Recipients cannot reshare notes belonging to another user.

Explicit sharing is permitted for both private and public notes. Public visibility and recipient-specific sharing are separate access mechanisms.

### 6.2 Reading a Shared Note

The backend must authorize access through the explicit share relationship only when:

- The share exists and `revoked_at IS NULL`.
- The note is not soft-deleted.
- The recipient account is active and not soft-deleted.
- The note owner's account is active and not soft-deleted.

Any suspension or soft deletion of the recipient or note owner blocks access through the share. Restoring an account restores eligibility, provided the share remains active and the note is available.

A public note may remain accessible through its independent public-visibility rules even when a particular explicit share has been revoked. Revoking a share does not make a public note private.

### 6.3 Revocation

- Only the note owner may revoke a share.
- Set `revoked_at` using PostgreSQL `NOW()`.
- Deny access through the revoked share immediately.
- Ensure authorization does not rely on stale cached permissions after revocation.
- Preserve the revoked record for historical reference.

### 6.4 Re-sharing

If an existing share has been revoked, the owner can share the note again.

The backend inserts a new row instead of reactivating the previous record. The unique partial index ensures that only one active share can exist for a given note-recipient pair.

## 7. Soft Deletion and Account Lifecycle

| Event                           | Share-record behavior                    | Access behavior                                      |
| ------------------------------- | ---------------------------------------- | ---------------------------------------------------- |
| Note soft-deleted               | No change                                | Block access through shares                          |
| Note restored                   | No change                                | Previously active shares become usable again         |
| Recipient soft-deleted          | No change                                | Block recipient access                               |
| Recipient restored              | No change                                | Previously active shares become usable again         |
| Owner suspended or soft-deleted | No change                                | Block access through shares                          |
| Owner restored or unsuspended   | No change                                | Restore eligibility for active shares                |
| Share revoked                   | Set `revoked_at`                         | Block access through that share                      |
| Share recreated                 | Insert a new row                         | Access resumes through the new active share          |
| Note permanently deleted        | Cascade-delete associated shares         | Share records no longer exist                        |
| Recipient permanently deleted   | Explicitly remove dependent shares first | Historical share records for that recipient are lost |

All restoration behavior remains subject to the share being active and all applicable authorization checks passing.

## 8. Timestamp Strategy

### Creation

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
```

PostgreSQL generates the creation timestamp. Client-provided timestamps should not be trusted for this purpose.

### Revocation

Use a database-side update:

```sql
UPDATE note_shares
SET revoked_at = NOW()
WHERE public_id = $1
  AND revoked_at IS NULL;
```

The backend must separately authorize the note owner before executing this operation. The example uses a parameterized query; `$1` represents the share's public UUID.

PostgreSQL's `NOW()` returns the transaction start timestamp. The check constraint validates timestamp ordering. For unusually long-running transactions, the application should account for transaction-consistent timestamp semantics.

No `updated_at` column or shared update trigger is required for this table.

## 9. Concurrency and Error Handling

The database is the final authority for active-share uniqueness.

If concurrent requests attempt to create the same active share, one insert may fail with PostgreSQL's unique-constraint violation. The backend should handle that failure gracefully rather than relying exclusively on a preliminary existence check.

Other relevant conditions include:

- Unknown recipient handle.
- Ineligible recipient account.
- Requester does not own the note.
- Self-sharing attempt.
- Note unavailable or soft-deleted.
- Share already revoked.
- Invalid revocation timestamp.
- Permanent deletion blocked by dependent records.

Return consistent API errors without exposing internal database details.

## 10. Security Considerations

- A public UUID is an identifier, not an authorization token.
- Every share-management operation requires authentication and ownership checks.
- Every shared-note read requires current authorization.
- Recipient handles must be resolved server-side; internal IDs must not be trusted from unverified client input.
- Avoid exposing whether a particular account exists where doing so would create an account-enumeration risk.
- Cache invalidation or authorization revalidation must prevent revoked shares from remaining usable through stale cached access.
- Public-note access must remain separate from explicit-share access.

## 11. Deliberately Excluded Fields

| Field                | Reason                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------ |
| `owner_user_id`      | Resolved through `notes.user_id`                                                           |
| `permission`         | View-only access is the sole supported permission                                          |
| `updated_at`         | Current lifecycle requires only creation and revocation timestamps                         |
| `revoked_by_user_id` | Explicit revocation actor tracking is outside the current scope                            |
| `previous_share_id`  | Each sharing period is an independent record                                               |
| `deleted_at`         | Revocation is modeled by `revoked_at`; separate soft deletion of share rows is unnecessary |

## 12. Implementation Notes

- Implement the schema using Drizzle ORM migrations.
- Ensure `gen_random_uuid()` is available in the target PostgreSQL environment.
- Keep backend authorization logic consistent with the lifecycle rules in this document.
- Add automated tests for duplicate active shares, revocation, re-sharing, soft deletion, restoration, owner authorization, and account deletion.
- Validate index usage with representative queries and `EXPLAIN ANALYZE` as data volume grows.
- Keep permanent deletion workflows transactional where practical and resolve all restrictive foreign-key dependencies.
