# Quiz Question Options Database Schema

**Project:** NoteGenius  
**Document:** `quiz-question-options-schema.md`  
**Version:** 1.0  
**Status:** Confirmed design draft  
**Database:** PostgreSQL  
**ORM:** Drizzle ORM

---

## 1. Overview

The `quiz_question_options` table stores the answer options associated with questions in NoteGenius quizzes.

Each option belongs to exactly one question. Correct options are identified through the separate `quiz_question_answers` table rather than a boolean column on the options table.

The schema supports both `single_choice` and `multiple_choice` questions.

## 2. Confirmed Design Decisions

| Decision                    | Specification                                               |
| --------------------------- | ----------------------------------------------------------- |
| Internal primary key        | `internal_id BIGSERIAL PRIMARY KEY`                         |
| Public identifier           | `public_id UUID NOT NULL UNIQUE DEFAULT gen_random_uuid()`  |
| Parent relationship         | `question_id BIGINT NOT NULL`                               |
| Parent deletion             | `ON DELETE CASCADE` from `quiz_questions`                   |
| Option ordering             | Positive, one-based `option_number`                         |
| Ordering uniqueness         | `UNIQUE (question_id, option_number)`                       |
| Option text                 | `option_text TEXT NOT NULL`                                 |
| Duplicate text              | Backend validation using normalized text comparison         |
| Minimum options             | 2, enforced by backend validation                           |
| Maximum options             | 4, enforced by backend validation                           |
| Correct-answer relationship | Separate `quiz_question_answers` table                      |
| Answer deletion             | Associated answer records cascade when an option is deleted |
| Creation timestamp          | `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`             |
| Update timestamp            | Omitted                                                     |
| Soft deletion               | No `deleted_at` column                                      |
| Database triggers           | Not used for option-count validation                        |

## 3. Table Definition

### 3.1 Columns

| Column          | PostgreSQL type | Constraints                                   | Purpose                         |
| --------------- | --------------- | --------------------------------------------- | ------------------------------- |
| `internal_id`   | `BIGSERIAL`     | Primary key                                   | Internal option identifier      |
| `public_id`     | `UUID`          | Not null, unique, default `gen_random_uuid()` | Public-facing option identifier |
| `question_id`   | `BIGINT`        | Not null, foreign key                         | Identifies the parent question  |
| `option_number` | `INTEGER`       | Not null, positive                            | Determines display order        |
| `option_text`   | `TEXT`          | Not null                                      | Text displayed to the learner   |
| `created_at`    | `TIMESTAMPTZ`   | Not null, default `NOW()`                     | Record creation timestamp       |

### 3.2 PostgreSQL DDL

```sql
CREATE TABLE quiz_question_options (
    internal_id BIGSERIAL PRIMARY KEY,

    public_id UUID NOT NULL UNIQUE
        DEFAULT gen_random_uuid(),

    question_id BIGINT NOT NULL
        REFERENCES quiz_questions(internal_id)
        ON DELETE CASCADE,

    option_number INTEGER NOT NULL
        CHECK (option_number >= 1),

    option_text TEXT NOT NULL,

    created_at TIMESTAMPTZ NOT NULL
        DEFAULT NOW(),

    CONSTRAINT uq_question_options_number
        UNIQUE (question_id, option_number),

    -- Supports the composite foreign key in quiz_question_answers.
    CONSTRAINT uq_question_options_question_internal
        UNIQUE (question_id, internal_id)
);
```

The final composite unique constraint supports referential integrity in `quiz_question_answers`, where the combination of `question_id` and `question_option_id` ensures that an answer references an option belonging to the same question.

Although `internal_id` is already unique, PostgreSQL requires a matching unique key for the composite foreign-key target.

## 4. Option Identity

### Internal identifier

`internal_id` is the database's internal identifier and is used for foreign-key relationships.

### Public identifier

`public_id` is a UUID intended for public-facing references where exposing sequential database identifiers should be avoided.

The UUID is generated by PostgreSQL using `gen_random_uuid()`.

## 5. Question Relationship and Deletion

The `question_id` foreign key references `quiz_questions.internal_id`.

```sql
FOREIGN KEY (question_id)
    REFERENCES quiz_questions(internal_id)
    ON DELETE CASCADE
```

Behavior:

- Every option must belong to an existing question.
- Permanently deleting a question automatically deletes its options.
- Soft-deleting a quiz does not automatically delete its questions or options.
- The application must enforce quiz and question access rules independently of physical deletion.

### Correct-answer deletion

The `quiz_question_answers` table references options through a composite foreign key:

```sql
FOREIGN KEY (question_id, question_option_id)
    REFERENCES quiz_question_options (question_id, internal_id)
    ON DELETE CASCADE
```

When an option is permanently deleted, the corresponding correct-answer record is deleted automatically.

The backend must then revalidate the question before its quiz can be marked `completed`.

## 6. Option Ordering

The `option_number` column determines the order in which options are presented.

Rules:

- Option numbers start at `1`.
- Option numbers must be positive.
- Two options belonging to the same question cannot share the same number.
- Options belonging to different questions may use the same number.

The database enforces these rules through:

```sql
CHECK (option_number >= 1);

UNIQUE (question_id, option_number);
```

The backend manages assignment and renumbering when options are created, reordered, or removed.

## 7. Option Count Validation

Each question must have between two and four options.

| Validation                 | Requirement |
| -------------------------- | ----------- |
| Minimum count              | 2 options   |
| Maximum count              | 4 options   |
| Generation validation      | Required    |
| Quiz completion validation | Required    |
| Database trigger           | Not used    |

These rules are enforced by backend validation because a normal row-level `CHECK` constraint cannot reliably enforce the number of related option rows.

The quiz must not transition to `completed` if any question violates the option-count rules.

## 8. Duplicate Option Text

The database does not enforce uniqueness on `option_text`.

Instead, the backend rejects duplicate option text using normalized text comparison.

The normalization logic should be consistent across AI generation, validation, and any future option-editing workflow.

This approach avoids relying on exact string equality when text may differ only in case or surrounding whitespace.

## 9. Timestamps and Deletion Policy

### Creation timestamp

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
```

The timestamp records when the option record was created.

### Update timestamp

No `updated_at` column is included. The current design does not require option-level modification timestamps.

### Soft deletion

No `deleted_at` column is included.

Options are removed through controlled application logic. Their associated correct-answer records are deleted through the confirmed foreign-key cascade, and the affected question is revalidated.

## 10. Indexing

The primary key and unique constraints create indexes for:

- `internal_id`
- `public_id`
- `(question_id, option_number)`
- `(question_id, internal_id)`

The unique index on `(question_id, option_number)` also supports retrieving a question's options in their defined order.

No additional index is required solely for that common query pattern. Review actual query plans before adding further indexes.

## 11. Backend Validation Checklist

Before a quiz is marked `completed`, the backend must verify:

1. Each question has between two and four options.
2. Every option has non-empty text after the application's agreed normalization and validation rules.
3. Option numbers are positive and unique within the question.
4. Duplicate normalized option text is rejected.
5. Every correct-answer record references an option belonging to its own question.
6. `single_choice` questions have exactly one correct option.
7. `multiple_choice` questions have at least two correct options.
8. Deleting an option triggers revalidation of the affected question.
9. A quiz with an invalid question cannot transition to `completed`.

Where validation and completion happen in the same workflow, use a transaction and suitable concurrency controls to prevent option changes from racing with completion validation.

## 12. Dependencies

This table depends on:

- `quiz_questions` — parent question records.
- `quiz_question_answers` — records identifying correct options.

The parent `quizzes` table indirectly controls the lifecycle of options through the quiz-to-question relationship.

Quiz attempts, learner responses, scoring history, sharing, and quiz-level generation status are outside the scope of this table.
